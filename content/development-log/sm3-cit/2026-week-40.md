## Weekly summary

This week I extended CIT from storing individual incidents to connecting them to users. I also introduced DAO interfaces, prepared an isolated database test setup and added an incident service for validation and application operations. This summary covers the work available through 3 October; the week is still in progress.

## What I implemented

- Added a `User` entity with an automatically generated ID, a required name and a required, unique email address.
- Linked each incident to a reporter through a required, unidirectional `ManyToOne` relationship. Several incidents can refer to the same user through `reported_by_id`.
- Added `UserDAO` methods for creating users and finding a user by email. Added a parameterised JPQL query in `IncidentDAO` to find incidents by reporter ID, ordered by incident ID.
- Introduced `IUserDAO` and `IIncidentDAO` to describe the available persistence operations. Incident CRUD remains in the DAO layer, with transactions and rollback for writes.
- Updated the manual example in `Main` to connect an incident to a stored user, retrieve it and list incidents belonging to that reporter.
- Added `IncidentService`, which depends on the DAO interfaces. It supports creating incidents, finding one or all incidents, listing by reporter, changing status and deleting incidents.

The service rejects blank titles and reporter emails, missing severity, descriptions longer than 2,000 characters, invalid IDs and null status values. It looks up an existing reporter before creation and throws an exception when a required user or incident cannot be found. New incidents retain the entity's default `OPEN` status.

## Testing progress

I added JUnit and Testcontainers support, plus a PostgreSQL test container and a Hibernate test configuration using `create-drop`. The current test checks that the container is running and the EntityManagerFactory is open.

This is the foundation for database integration tests. There are no assertions yet for incident CRUD, reporter filtering or service validation. The test suite was inspected, but was not executed for this report, so this entry does not claim a passing test run. The local move of `HibernateTestConfig` into `app.config` is present in the working tree but has not yet been committed.

## Technical choices and learning points

The reporter relationship connects the JPA model to the project domain: an incident belongs to a reporting user. It is kept unidirectional, without cascade operations, so the service finds an existing user before persisting an incident.

DAO interfaces separate the operation contracts from their database implementations. The service adds a place for input checks and application behaviour, while DAO methods handle persistence. This also provides a basis for testing the service independently later.

The test container gives the tests a separate database. Starting that database is only the first step; meaningful tests still need to assert the data and behaviour of each operation.

## Connection to the course

This week's implementation applies JPA Relations through the reporter relationship, DAO interfaces and JPQL queries. It also starts the testing work with an isolated database setup and prepares validation for a future REST layer.

The teaching schedule covers REST & Test in week 40, but CIT does not yet expose REST endpoints or contain REST Assured endpoint tests. The log records the project's actual progress rather than treating all course topics as completed features.
