## What I worked on

I worked on the foundation of SM3-CIT, my Cyber Incident Tracker project, using Java, JPA/Hibernate and PostgreSQL.

- Set up the project packages and an `Incident` entity with an ID, title and description.
- Implemented an `IncidentDAO` to create, find, list, update and delete incidents.
- Used database transactions with commit and rollback for operations that change data.
- Added a small program in `Main` to manually try out the CRUD flow using a test incident.

I confirmed that the CRUD flow worked before moving on to status and severity. This was a manual check, rather than an automated test suite.

## Challenges and lessons learned

One important distinction was between the Java entity and the database table: JPQL queries use the entity name `Incident`, while the table is named `incidents`.

I also worked through how `persist()` saves a new entity and `merge()` copies changes into an entity managed by the current `EntityManager`. Each DAO method opens and closes its own `EntityManager`.

## Status and severity

The next step was to make the data model more useful for tracking security incidents. I added enums for:

- **Status:** `OPEN`, `INVESTIGATING`, `CONTAINED`, `RESOLVED`.
- **Severity:** `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`.

The entity stores the enum names as text. New Java objects start with status `OPEN` and severity `MEDIUM`.

## Open issue

Existing database rows need attention before the new required fields can be used safely. Java default values do not automatically fill those fields in rows already stored in the database. Handling that change and checking the updated model remained the next step at the end of the session.

## Next steps

- Handle status and severity for existing database rows.
- Run the CRUD flow again with the updated fields.
- Add automated DAO tests after the manual flow is working.
